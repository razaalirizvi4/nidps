\chapter{High-Level and Low-Level Design}\label{chap:6}
\label{chap:design}
\noindent This chapter describes how the methodology of Chapter~\ref{chap:approach} is realised as software. It moves from the high level to the low level: first an overview of the system and the considerations that shaped its design, then the architecture of the whole system and of each subsystem, the strategies behind the main architectural decisions, the class diagram, and finally the policies and tactics that govern implementation, testing and maintenance.

\section{System Overview}\label{sec:6.1}
\label{sec:sysoverview}
\noindent The NIDPS is a self-contained security appliance that is created using software on a single Linux host. The host serves as an alternative to the home router's wireless network: clients connect to the NIDPS access point and the NIDPS forwards these connections, via its own NAT, to the existing ISP router, which continues to manage the internet connection. The client device and ISP router will not need to be modified.

\noindent In terms of functionality it does five things: it provides network access with wireless access point with DHCP, DNS and routing; it performs signature and anomaly analysis in line and also performs flow-level analysis of all traffic (encrypted and otherwise) through metadata; it fuses the results of signature, anomaly and classification, and comes up with a verdict on a per-flow basis and with a per-host risk score; it responds by automatically blocking offending addresses for a specific, escalating time; it reports and remains available, by showing live statistics and alerts on a web dashboard and maintaining a network in a defined state in case of component failures.

\noindent It's a system of independent services, not one big program, with an event bus that facilitates the communication between the services. The path for data packets to follow is kept as short as possible (kernel plus Suricata), and everything slower runs next to that path, rather than in it, such as machine learning, the database and the dashboard. Sections~\ref{sec:sysarch} and~\ref{sec:archstrategies} explain this choice in detail.

\section{Design Considerations}\label{sec:6.2}
\label{sec:designconsiderations}
\noindent The assumptions, constraints, goals and development methods that influenced the design are recorded in this section.

\subsection{Assumptions and Dependencies}\label{sec:6.2.1}
\label{sec:assumptions}
\begin{itemize}
    \item \textbf{Hardware:} The host has at least a quad-core 64-bit ARM or x86 CPU, 4\,GB of RAM, a wireless adapter that supports AP mode and an Ethernet port for the uplink.
    \item \textbf{Operating system:} Debian based Linux distribution with support for systemd, iptables and ipset in kernel.
    \item \textbf{Network position:} NIDPS is the only wireless network to which wireless network clients connect. Devices which are connected directly to the ISP router via cable or directly by the ISP router's Wi-Fi are not protected. To disable the ISP router's WiFi is part of the set-up process.
    \item \textbf{Third-party software:} Suricata 7 or greater with Emerging Threats Open ruleset, hostapd, dnsmasq, Python 3.11+ with scikit-learn and XGBoost. The ruleset needs to be updated periodically from the Internet.
    \item \textbf{End users:} Owner has NO security expertise. Defaults should be safe and not require tuning, and dashboard should provide information about alerts in easy-to-understand terms.
    \item \textbf{Trust:} The NIDPS host and admin's devices are trusted. The ISP router is assumed to be operational but will not be considered as being trustworthy for any security.
    \item \textbf{Likely changes:} Changes are likely to include new attack types and new rules, models may be retrained and the TLS fingerprinting method could change from JA3 to its successor JA4, as TLS client libraries start to shuffle the order of extensions. All these are separated by the design of their components.
\end{itemize}

\subsection{Goals and Guidelines}\label{sec:6.2.3}
\label{sec:goals}
\noindent The objectives and principles are as follows. The network is never allowed to be worse than a plain router: all design decisions are evaluated against this, which is why fail-open is the default, why blocks expire and why the number of blocks per minute is capped. Only the kernel and Suricata sit in the forwarding path; everything that might be done afterwards is shifted out of it. Each layer is intended to guard against the vulnerabilities of another layer, because no one detector is relied upon to detect everything (Section~\ref{sec:overview}). In order to fit the hardware, the model sizes are limited and loaded into memory to eliminate disk access during analysis. Each block documents the decision made, the reasons for that decision, and supporting evidence, allowing the owner to trust or challenge the decision. Features are computed by one implementation to rule out train/serve skew. Thresholds, failure mode and block durations are configurable, but the defaults work by default.

\subsection{Development Methods}\label{sec:6.2.4}
\label{sec:devmethods}
\noindent The project is executed in short sprints of two weeks, consistent with the FYP milestones, and is iterative and incremental in nature. The various steps represent working vertical slices: access point with Suricata (Layer 1), flow extraction and Layer 2, Layer 3, fusion and enforcement, watchdog and dashboard. As a result of this order, the system will be protected from the first increment onwards and each subsequent increment will be quantifiable against a working baseline.

\noindent To build a good model, the machine learning process is implemented based on the CRISP-DM methodology, which consists of the following steps: data understanding, data preparation, modelling, evaluation and deployment. A simple waterfall model was thought of but rejected: requirements like thresholds and feature sets cannot be known beforehand, as detection performance will be as seen on real traffic.

\subsection{Subsystem Architecture}\label{sec:6.3.1}
\label{sec:subsysarch}
\noindent This section describes each subsystem in more detail.

\subsubsection{Network Access and Data Plane}\label{sec:6.3.1.1}
\noindent The main part of this subsystem consists of configuring the existing Linux components, with the exception of the new netfilter rule layout and management. Figure~\ref{fig:packetpath} traces one packet from a client to the internet.

\begin{figure}[!htbp]
    \centering
    \includegraphics[width=\textwidth]{Figures/nidps_fig6_2.pdf}
    \caption{Packet path through the data plane.}
    \label{fig:packetpath}
\end{figure}

\noindent The order of the rules is important: the ipset check is executed first, so if a packet comes from a blocked host it is dropped in the kernel and doesn't use any CPU in Suricata. This allows the inspection engine to remain available for other traffic during a DDoS attack from a blocked address.

\subsubsection{Detection Subsystem}\label{sec:6.3.1.2}
\noindent There are four producers in the detection subsystem. Suricata and the ARP monitor issue alerts directly. The flow extractor will publish flow records, and the ML scorer will enhance the flow records and publish them. The ML scorer consists of three sub-components internally:
\begin{itemize}
    \item \textbf{Feature validator:} Validates each flow record against the feature schema contained in the model and rejects the flow record if it does not match or is malformed.
    \item \textbf{Flow models:} Once loaded at start-up, they are applied to each flow record, according to the Isolation Forest and the RF/XGBoost classifier.
    \item \textbf{Host behaviour tracker:} Maintains per-host state (baseline of exfiltrated bytes, timestamps of connections, local JA3 counts) and calculates the exfiltration and beaconing scores of Sections~\ref{sec:exfil} and~\ref{sec:beacon} respectively. Its state is bounded: When inactive host/keys are entered, they expire.
\end{itemize}

\subsubsection{Decision and Response Subsystem}\label{sec:6.3.1.3}
\noindent The decision engine consumes all evidence from the bus, joins Suricata alerts with flow records by flow identifier and time, runs Algorithm~\ref{alg:verdict} and maintains the host scores of Section~\ref{sec:hostscore}. The enforcer receives BLOCK verdicts and runs Algorithm~\ref{alg:block}. The two are kept separate so that the component allowed to change firewall state is small, simple and easy to audit.

\subsubsection{Reliability Subsystem}\label{sec:6.3.1.4}
\noindent While the watchdog has application-level health (queue depth, processing lag) information and determines when to switch to degraded mode, systemd has process level supervision (automatic restart, start order, resource limits). The Failure mode at the kernel level (queue bypass on or off) is set at start up of the data plane and is not related to the presence of the watchdog.

\subsubsection{Management and Reporting Subsystem}\label{sec:6.3.1.5}
\noindent The Dashboard API is only available on the LAN side. It counts live flows per second, alerts and blocks per layer, shows an alert list with the evidence used for each verdict, has a list of currently blocked hosts with an unblock action, presents the host risk scores, displays the health status of the components and allows you to set thresholds, failure mode and an allowlist. Configurations are checked, saved and posted on the bus for running services to get.

\subsubsection{Offline Training Pipeline}\label{sec:6.3.1.6}
\noindent Figure~\ref{fig:training} shows the offline pipeline and the hand-over of models to the device.

\begin{figure}[H]
    \centering
    \includegraphics[width=0.9\textwidth]{Figures/nidps_fig6_3.png}
    \caption{Offline training pipeline and model hand-over to the device.}

\noindent Training is performed on a workstation as opposed to the NIDPS host, as it requires significantly more memory. Only a model package containing the model file, its feature schema and a version manifest is handed over to the device.

\section{Architectural Strategies}\label{sec:6.4}
\label{sec:archstrategies}
\noindent Each strategy below notes the decision made, the rationale for the decision and what was rejected.

\subsection{Layered Defence with a Short Fast Path}\label{sec:6.4.1}
\noindent \textbf{Decision:} Detection is divided into a packet-level layer on the forwarding path (Suricata) and flow-level layers off the forwarding path (ML), with a fusion layer.

\noindent \textbf{Reasoning:} For every packet forwarded the CPU budget would be incurred and extra latency would be added to each connection, defeating the first goal (Section~\ref{sec:goals}). The only forwarding latency penalty for flow-level ML off the path will be the cost of the Suricata rule that must be applied to the first packet.

\noindent \textbf{Alternatives rejected:} ML-only inline detection (too slow, and not protecting against known attacks); Suricata-only detection (missing zero-day or behavioural attacks).
\subsection{Metadata-Only Analysis of Encrypted Traffic}\label{sec:6.4.2}
\noindent \textbf{Decision:} Encrypted traffic analysed only using JA3/JA3S fingerprints and flow statistics.

\noindent \textbf{Reviewing the reasons:} TLS interception would require a trusted root certificate on every client, wouldn't work with certificate pinning, and would increase CPU load on clients. It would also allow for all the traffic to be displayed in plain text from all devices in the household, which would be a huge privacy hazard.

\noindent \textbf{Rejected alternatives:} Full TLS interception (above); ignoring encrypted traffic (most C2 now uses TLS). Known limitation: TLS extension order is now randomised by browsers, reducing the stability of JA3 for browser traffic. Since the fingerprinting is separated from the rest of the flow extractor, other components can remain the same and JA4 can be changed to sort extensions before hashing.

\subsection{Offline Training, Online Inference}\label{sec:6.4.3}
\noindent \textbf{Decision:} Models to be trained on a workstation and deployed as read-only versioned packages. The device is capable of only doing inference and threshold calibration.

\noindent \textbf{Reasoning:} A training process of hundreds of millions of flows requires much more memory than the device available. Online retraining on a device will also enable an adversary to slowly condition the model to think that malicious traffic is acceptable (model poisoning). Narrowing the threshold alone is slightly riskier, but addresses the local network (Section~\ref{sec:calibration}).

\noindent \textbf{Rejected:} Continuous online learning (poisoning risk, cost of hardware); a fixed global threshold (false positives with real home traffic).

\subsection{Local Services Connected by an Event Bus}\label{sec:6.4.4}
\noindent \textbf{Decision:} Each component is its own systemd service and message exchange is handled via a local publish/subscribe bus. Redis Streams is the proposed implementation.

\noindent \textbf{Failure modes:} Service isolation means one service can crash without affecting the others, and systemd can restart each service independently. Redis Streams is lightweight, has a bounded backlog which a restarted consumer can resume from, and allows consumer groups (including the dashboard and the decision engine) to read the same events independently.

\noindent \textbf{Alternatives that were rejected:} Direct function calls in one process (no fault isolation); Apache Kafka (too heavy for the hardware); plain unix sockets between each pair of components (simple, but every new consumer requires new wiring, and when a consumer restarts, messages are lost).

\subsection{Kernel-Enforced Blocking and Failure Semantics}\label{sec:6.4.5}
\noindent \textbf{Decision:} Blocking and failure (ipset with timeouts, and NFQUEUE bypass or not) are both managed by the kernel and not user space software.

\noindent \textbf{Reasoning:} User space programs can crash but the kernel continues to run. While the queue-bypass flag applies the selected mode regardless of whether the watchdog is down or not, timed ipset entries expire even if the enforcer fails.

\noindent \textbf{Alternatives that were considered but rejected:} Adding iptables rules per blocked host (slow if lots of hosts are blocked and iptables rules stay present after a crash); a user space proxy that drops traffic (adds latency and is itself a crash risk).

\subsection{Error Detection and Recovery}\label{sec:6.4.7}
\noindent There are three levels at which errors are dealt with.
\begin{enumerate}
    \item \textbf{Record level:} The feature validator rejects and counts malformed flow records or alerts, never passing them to models.
    \item \textbf{Component level:} Heartbeats and systemd supervision detect crashes and hangs and restart the component (Section~\ref{sec:failure}).
    \item \textbf{Failure mode:} How traffic behaves when a component is down is specified at the system level.
\end{enumerate}
\noindent At all three levels, logs will be written to the event store and as such, will show up on the dashboard when the system is not fully protected.

\subsection{Data Storage, Persistence and Retention}\label{sec:6.4.8}
\label{sec:storage}
\noindent We only store derived data: block information, risk history per host, calibration state and configuration, decisions, alarms and verdicts. On normal operation, there is no packet data or payload stored. The flow data is stored in a relatively short rolling window (for example, 7 days) to be used for analysis and calibration before being purged. This gives a good degree of privacy to domestic users and puts a reasonable amount of data on a small storage device.

\subsection{Future Extension}\label{sec:6.4.9}
\noindent The system is designed to allow the most likely extensions to be added by adding functionality and not modifying existing functionality. A new detector is connected to the bus. A new response (like a notification to the owner's phone) subscribes to decisions. A new extractor for support of a new model or new JA4 will be added.

Evidence is converted into a Verdict by the DecisionEngine and BLOCK verdicts are converted into BlockEntry entries by the Enforcer.

\section{Policies and Tactics}\label{sec:6.6}
\label{sec:policies}
\noindent The following policies only have an impact on parts of the implementation and do not alter the structure of the system as such:

\subsection{Rule and Threshold Management}\label{sec:6.6.1}
\noindent A scheduled job would update the ET Open ruleset daily, it would be syntax tested with Suricata's test mode, and it would be loaded via a live rule reload, so there won't be any inspection that will fail to occur. In case of failure, the last ruleset is still in effect. Custom rules are kept in a separate file in version control, they will not be overwritten by any ET rules changes. All numeric thresholds (rule thresholds, flow timeouts $T_a$ and $T_i$, $\tau$, $\theta$ values, $\Theta$, block durations) are read from a single configuration file that has documented defaults.

\subsection{Model Packaging and Versioning}\label{sec:6.6.2}
\label{sec:modelpackaging}
\noindent Each model package contains the model file, the list of features ordered by version of the extractor, the class list and the training date and metrics. If there is a package at load time which does not contain the desired features, the ML scorer rejects the package. XGBoost models are stored as a native JSON file and not as Python pickles, because loading a pickle can run arbitrary code. scikit-learn models are stored in joblib files and are only loaded from a registry directory that can only be written to by the deployment user. If the model fails, the last package is saved to be rolled back.

\subsection{Engineering Trade-offs}\label{sec:6.6.3}
\begin{itemize}
    \item \textbf{Detection speed vs.\ accuracy:} ML verdicts are per flow, not per packet (Section~\ref{sec:mltiming}), compromising a small amount of delay for ML-detected attacks, and eliminating any extra forward delay.
    \item \textbf{False positives vs.\ missed attacks:} The calibration percentile $p$ and the block thresholds are the explicit controls. Defaults prefer fewer false positives as the loss of trust on a home network is fast.
    \item \textbf{Availability vs.\ security:} Selected at deployment time (failure mode), default is fail-open for homes.
\end{itemize}

\subsection{Coding Guidelines and Conventions}\label{sec:6.6.4}
\noindent The Python code follows PEP 8, and is checked for types using a linter and type-checker as part of the continuous integration. Every service is an independent package and has only one entry point exposed. All messages sent through the event bus are versioned JSON messages with a schema. This enables the producers and consumers to be upgraded individually. All logging is in the form of structured JSON containing a timestamp, a component name and identifier for either a flow or host. This allows events to be tracked via services.

\subsection{Testing Plan}\label{sec:6.6.6}
\begin{enumerate}
    \item \textbf{Unit tests for each algorithm:} Flow assembly on crafted PCAPs, JA3 computation on published reference hashes, threshold calibration, fusion rules and the enforcer's allowlist, rate limit and back-off.
    \item \textbf{Integration tests:} Play back labelled PCAPs throughout the system on a test system and compare with labelled results.
    \item \textbf{Live attack tests:} Involve launching each in-scope attack from the attacker side onto our test systems on the isolated test network.
    \item \textbf{Performance tests:} For latency, throughput and resource use (Table~\ref{tab:sysperf}).
    \item \textbf{Fault-injection tests:} For each failure mode, each service is killed or frozen under load, and the recovery time and traffic impact are measured.
    \item \textbf{Soak test:} The system is run for a minimum of one week on a real home network on an alert-only basis to gauge false positives before blocking is enabled.
\end{enumerate}

\subsection{Build and Deployment}\label{sec:6.6.8}
\noindent It is deployed on a clean Debian image, with only one installation script that installs system packages (Suricata, hostapd, dnsmasq, ipset, Redis), creates a Python virtual environment, installs pinned versions of dependencies, copies the configuration and the active model package, and activates the systemd units in dependency order (data plane, Suricata, rest). One service at a time is upgraded and that service is restarted. Every service is supervised and the failure mode is enforced at kernel level, which means that the network does not lose any behaviour after an upgrade.

\subsection{Maintenance}\label{sec:6.6.9}
\noindent Routine maintenance is automated: daily rule updates, weekly threshold recalibration (see Algorithm~\ref{alg:calibration}), and purging logs and flow-records outside of the retention window. Models are retrained offline when new datasets are available, or the dashboard indicates that the alert rate is increasing that is not explained by calibration, or when new classes of attacks become available. The health history report on the Dashboard indicates to the owner when the system was operating in a degraded or failed condition.

\section{Conclusion}\label{sec:6.7}
\label{sec:ch6conclusion}
\noindent In this chapter we translated the methodology of Chapter~\ref{chap:approach} into a concrete design. The NIDPS is a single Linux host, with five runtime subsystems (data plane, detection, decision and response, management and reporting, and reliability), and an offline training pipeline. The main architectural decisions are that the forwarding path is short, encrypted traffic is analysed only via metadata, that training is done offline and thresholds are be calibrated online, that components are separated with the supervised services communicating with each other via an event bus, and that blocking and failure behaviour is controlled by the kernel. The class diagram establishes a common Detector interface which allows quick addition of new detectors, and restricts the number of firewall changes to only one Enforcer. The policies relating to rule and model management, testing, traceability and deployment complete the design, and link each policy goal with the component responsible for it and the test for it.
