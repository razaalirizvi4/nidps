\chapter{High-Level and Low-Level Design}\label{chap:6}
\label{chap:design}
\noindent This chapter describes how the methodology of Chapter~\ref{chap:approach} is realised as software. It moves from the high level to the low level: first an overview of the system and the considerations that shaped its design, then the architecture of the whole system and of each subsystem, the strategies behind the main architectural decisions, the class diagram, and finally the policies and tactics that govern implementation, testing and maintenance.

\section{System Overview}\label{sec:6.1}
\label{sec:sysoverview}
\noindent The NIDPS is a self-contained security appliance built from software on a single Linux host. The host replaces the role of the home router's wireless network: clients connect to the NIDPS access point, and the NIDPS routes their traffic, through its own NAT, to the existing ISP router, which keeps handling the internet connection. No change is needed on client devices or on the ISP router.

\noindent Functionally, the system does five things:
\begin{enumerate}
    \item \textbf{Provides network access:} a wireless access point with DHCP, DNS and routing.
    \item \textbf{Inspects traffic:} inline signature inspection of every packet, plus flow-level analysis of all traffic, including encrypted traffic through metadata.
    \item \textbf{Decides:} fuses signature, anomaly and classification results into a per-flow verdict and a per-host risk score.
    \item \textbf{Responds:} blocks offending addresses automatically for a limited, escalating time.
    \item \textbf{Reports and stays available:} shows live statistics and alerts on a web dashboard, and keeps the network in a defined state when a component fails.
\end{enumerate}

\noindent The system is made up of independent services connected by a local event bus, rather than as one large program. The packet-forwarding path is kept as short as possible (kernel plus Suricata), and everything slower like machine learning, the database and the dashboard, sits beside that path instead of in it. Sections~\ref{sec:sysarch} and~\ref{sec:archstrategies} explain this choice in detail.

\section{Design Considerations}\label{sec:6.2}
\label{sec:designconsiderations}
\noindent This section records the assumptions, constraints, goals and development methods that shaped the design.

\subsection{Assumptions and Dependencies}\label{sec:6.2.1}
\label{sec:assumptions}
\begin{itemize}
    \item \textbf{Hardware:} the host has at least a quad-core 64-bit ARM or x86 CPU, 4\,GB of RAM, a wireless adapter that supports AP mode and an Ethernet port for the uplink.
    \item \textbf{Operating system:} Debian based Linux distribution with systemd, iptables (use of nftables is accepted, but not required), ipset (use of NFQUEUE is accepted, but not required) and support in the kernel.
    \item \textbf{Network position:} NIDPS is the only wireless network clients access. Devices which are connected directly to the ISP router via cable or directly by the ISP router's Wi-Fi are not protected. Turning off the ISP router's WiFi is a part of the set-up process.
    \item \textbf{Third-party software:} Suricata 7 or later with Emerging Threats Open ruleset, hostapd, dnsmasq, Python 3.11+ with scikit-learn and XGBoost. Periodic Internet access is required for ruleset updates.
    \item \textbf{End users:} Owner is NOT a security expert. Defaults should be safe and not require tuning, and dashboard should provide information about alerts in easy-to-understand terms.
    \item \textbf{Trust:} The NIDPS host and the admin's devices are trusted. The ISP router is assumed to be working, but is not trusted to provide any security.
    \item \textbf{Likely changes:} Changes are likely to include new attack types and new rules, models may be retrained and the TLS fingerprinting method could change from JA3 to its successor JA4, as TLS client libraries start to shuffle the order of extensions. Each of these is isolated by the design behind its component.
\end{itemize}

\subsection{Goals and Guidelines}\label{sec:6.2.3}
\label{sec:goals}
\begin{enumerate}
    \item \textbf{Never make the network worse than a plain router.} Every design choice is checked against this. It is why fail-open is the default, why blocks expire and why the number of blocks per minute is capped.
    \item \textbf{Keep the fast path short (KISS).} Only the kernel and Suricata sit in the forwarding path. Anything that can be done after the fact is moved off it.
    \item \textbf{Defence in depth.} Each layer covers a weakness of another layer as no single detector is trusted to catch everything (Section~\ref{sec:overview}).
    \item \textbf{Speed over memory where the two conflict, within a fixed budget.} In order to fit the hardware, the model sizes are capped and loaded fully in memory to avoid disk access during anlysis.
    \item \textbf{Explainable decisions.} Every block records which layer decided, why, and with what evidence, so the owner can trust or override it.
    \item \textbf{Same code for training and serving.} Features are computed by one implementation to rule out train/serve skew.
    \item \textbf{Configurable, safe defaults.} Thresholds, failure mode and block durations are configurable, but the defaults work by default.
\end{enumerate}

\subsection{Development Methods}\label{sec:6.2.4}
\label{sec:devmethods}
\noindent The project follows an iterative, incremental approach in short sprints of two weeks, aligned with the FYP milestones. Each increment delivers a working vertical slice: first the access point with Suricata (Layer 1, completed), then flow extraction and Layer 2, then Layer 3, then fusion and enforcement, and finally the watchdog and dashboard. This order means the system protects the network from the first increment onwards and every later layer can be measured against a working baseline.

\noindent The machine learning work follows the CRISP-DM cycle (data understanding, preparation, modelling, evaluation, deployment), because model quality depends on several rounds of data cleaning and re-evaluation. A plain waterfall model was considered and rejected: detection performance on real traffic cannot be known in advance, so requirements such as thresholds and feature sets must be allowed to change as results come in.

\noindent There are two ways in which the subsystems work together. The forwarding path is entirely in kernel and Suricata and there is only one feedback loop from the enforcer to ipset. Everything else is communicated via the local event bus: detectors publish evidence, decision engine consumes it and publishes verdicts, and the rest (dashboard and event store) subscribe to it.
\noindent \textbf{Rationale and rejected alternatives.} The easiest was to write was a \emph{single monolithic process} where one crash in ML would bring down detection altogether, and memory would be all shared by everything. A \emph{distributed design} that has an independent analysis server would enable larger models, but would require a second machine, network latency and cost, which is counter to the project's goal of having just one affordable box. The selected \emph{local service oriented design} localizes failures per service and ensures that everything is on one host, which is exactly what the failure handling requirement requires.

\subsection{Subsystem Architecture}\label{sec:6.3.1}
\label{sec:subsysarch}
\noindent This section describes each subsystem in more detail.

\subsubsection{Network Access and Data Plane}\label{sec:6.3.1.1}
\noindent This subsystem is mostly configuration of existing Linux components; the new parts are the netfilter rule layout and its management. Figure~\ref{fig:packetpath} traces one packet from a client to the internet.

\begin{figure}[!htbp]
    \centering
    \includegraphics[width=0.85\textwidth]{Figures/nidps_fig6_2.png}
    \caption{Packet path through the data plane.}
    \label{fig:packetpath}
\end{figure}

\noindent The rule order matters: the ipset check comes before the queue, so packets from blocked hosts are discarded in the kernel and never cost Suricata any CPU. During a DDoS from a blocked source, this keeps the inspection engine free for other traffic.

\subsubsection{Detection Subsystem}\label{sec:6.3.1.2}
\noindent There are four producers in the detection subsystem. Suricata and the ARP monitor issue alerts directly. The flow extractor will publish flow records, and the ML scorer will enhance the flow records and publish them. The ML scorer consists of three sub-components internally:
\begin{itemize}
    \item \textbf{Feature validator:} validates each flow record against the feature schema contained in the model and rejects the flow record if it does not match or is malformed.
    \item \textbf{Flow models:} once loaded at start-up, they are applied to each flow record, according to the Isolation Forest and the RF/XGBoost classifier.
    \item \textbf{Host behaviour tracker:} maintains per-host state (baseline of exfiltrated bytes, timestamps of connections, local JA3 counts) and calculates the exfiltration and beaconing scores of Sections~\ref{sec:exfil} and~\ref{sec:beacon} respectively. Its state is bounded: When inactive host/keys are entered, they expire.
\end{itemize}

\subsubsection{Decision and Response Subsystem}\label{sec:6.3.1.3}
\noindent The decision engine consumes all evidence from the bus, joins Suricata alerts with flow records by flow identifier and time, runs Algorithm~\ref{alg:verdict} and maintains the host scores of Section~\ref{sec:hostscore}. The enforcer receives BLOCK verdicts and runs Algorithm~\ref{alg:block}. The two are kept separate so that the component allowed to change firewall state is small, simple and easy to audit.

\subsubsection{Reliability Subsystem}\label{sec:6.3.1.4}
\noindent While the watchdog has application-level health (queue depth, processing lag) information and determines when to switch to degraded mode, systemd has process level supervision (automatic restart, start order, resource limits). The Failure mode at the kernel level (queue bypass on or off) is set during start up of the data plane and is not dependent on the presence of the watchdog.

\subsubsection{Management and Reporting Subsystem}\label{sec:6.3.1.5}
\noindent The Dashboard API is only available on the LAN side. It counts live flows per second, alerts and blocks per layer, shows an alert list with the evidence used for the verdict, has a list of currently blocked hosts with an unblock action, presents the host risk scores, displays the health status of the components and allows you to set thresholds, failure mode and an allowlist. Configurations are checked, saved and posted on the bus for running services to get.

\subsubsection{Offline Training Pipeline}\label{sec:6.3.1.6}
\noindent Figure~\ref{fig:training} shows the offline pipeline and the hand-over of models to the device.

\begin{figure}[!htbp]
    \centering
    \includegraphics[width=0.9\textwidth]{Figures/nidps_fig6_3.png}
    \caption{Offline training pipeline and model hand-over to the device.}

\noindent Training runs on a workstation, not on the NIDPS host, because it needs far more memory than inference. The only hand-over to the device is a model package containing the model file, its feature schema and a version manifest.

\section{Architectural Strategies}\label{sec:6.4}
\label{sec:archstrategies}
\noindent Each strategy below notes the decision made, the rationale for the decision and what was rejected.

\subsection{Layered Defence with a Short Fast Path}\label{sec:6.4.1}
\noindent \textbf{Decision:} detection is divided into a packet-level layer on the forwarding path (Suricata) and flow-level layers off the forwarding path (ML), with a fusion layer.

\noindent \textbf{Reasoning:} ML inference on each of the forwarded packets would make it impossible to stay within the CPU budget, and would introduce additional latency to each connection, contradicting the first objective of Section~\ref{sec:goals}. The only forwarding latency cost for flow-level ML outside the path will be the cost of the Suricata rule that must be applied to the first packet.

\noindent \textbf{Alternatives rejected:} ML-only inline detection (too slow, and no immediate protection against known attacks); Suricata-only detection (misses zero-day and behavioural attacks).
\subsection{Metadata-Only Analysis of Encrypted Traffic}\label{sec:6.4.2}
\noindent \textbf{Decision:} encrypted traffic analysed only using JA3/JA3S fingerprints and flow statistics.

\noindent \textbf{Reasoning:} TLS interception would involve trusted root certificate on each client, would not be compatible with certificate pinning, would break some IoT devices and would increase CPU load. It would also allow for all the traffic to be displayed in plain text from all devices in the household, which would be a huge privacy hazard.

\noindent \textbf{Alternatives rejected:} full TLS interception (above); ignoring encrypted traffic (most C2 now uses TLS). Known limitation: browsers now randomise TLS extension order making JA3 less stable for browser traffic. Since the fingerprinting is separated from the rest of the flow extractor, other components can remain the same and JA4 can be changed to sort extensions before hashing.

\subsection{Offline Training, Online Inference}\label{sec:6.4.3}
\noindent \textbf{Decision:}models to be trained on a workstation and deployed as read-only versioned packages. The device can only do inference and threshold calibration.

\noindent \textbf{Reasoning:} A training process of hundreds of millions of flows requires much more memory than the device available. Online retraining on a device will also enable an adversary to slowly condition the model to think that malicious traffic is acceptable (model poisoning). Calibrating just the threshold (Section~\ref{sec:calibration}) adapts to the local network with limited risk.

\noindent \textbf{Alternatives rejected:} Continuous online learning (poisoning risk, cost of hardware); a fixed global threshold (false positives with real home traffic).

\subsection{Local Services Connected by an Event Bus}\label{sec:6.4.4}
\noindent \textbf{Decision:} each component is its own systemd service and message exchange is handled via a local publish/subscribe bus. Redis Streams is the proposed implementation.

\noindent \textbf{Reasoning:} The failure modes require service isolation, which is where one service can crash without impacting the others, and where systemd can restart each service independently. The bus separates the producers from the consumers. Redis Streams is lightweight, has a bounded backlog which a restarted consumer can resume from and allows for consumer groups that run the dashboard and the decision engine independently, reading the same events.

\noindent \textbf{Alternatives rejected:} direct function calls in one process (no fault isolation); Apache Kafka (too heavy for the hardware); plain unix sockets between each pair of components (simple, but every new consumer requires new wiring, and while a consumer restarts, messages are lost).

\subsection{Kernel-Enforced Blocking and Failure Semantics}\label{sec:6.4.5}
\noindent \textbf{Decision:} blocking and failure (ipset with timeouts, and NFQUEUE bypass or not) are both handled by the kernel and not user space software.

\noindent \textbf{Reasoning:} user space programs can crash but the kernel continues to run. While the queue-bypass flag applies the selected mode regardless of whether the watchdog is down or not, timed ipsets entries expire even if the enforcer fails.

\noindent \textbf{Alternatives rejected:} Add iptables rules one per blocked host (slow when many hosts are blocked and iptables rules are still there after a crash); A user-space proxy that drops traffic (adds latency and is itself a crash risk).

\subsection{Error Detection and Recovery}\label{sec:6.4.7}
\noindent There are three levels at which errors are dealt with.
\begin{enumerate}
    \item \textbf{Record level:} malformed flow records or alerts are rejected by the feature validator and counted, never passed to models.
    \item \textbf{Component level:} heartbeats and systemd supervision detect crashes and hangs and restart the component (Section~\ref{sec:failure}).
    \item \textbf{System level:} the system level (kernel-enforced failure mode) determines the fate of traffic when a component is down. All three levels will log to the event store and hence the dashboard will display when the system was not completely protected.
\end{enumerate}

\subsection{Data Storage, Persistence and Retention}\label{sec:6.4.8}
\label{sec:storage}
\noindent We only store derived data: block information, risk history per host, calibration state and configuration, decisions, alarms and verdicts. No packet data or payload is stored on normal operation. Flow data is stored in a relatively short rolling window (e.g. 7 days) for analysis and calibration purposes before being purged. This provides an effective level of privacy for domestic users whilst placing a reasonable amount of data on a small storage device.

\subsection{Future Extension}\label{sec:6.4.9}
\noindentThe system is structured to make the most probable extensions accomplished by adding functionality rather than modifying functionality. A new detector emits to the bus. A new response (e.g. notification to the owner's phone) subscribes to decisions. A new extractor for support of a new JA4 or new model is added.

\section{Policies and Tactics}\label{sec:6.6}
\label{sec:policies}
\noindent The following policies only influence aspects of the implementation and do not change the overall structure of the system.

\subsection{Rule and Threshold Management}\label{sec:6.6.1}
\noindent A scheduled job updates the ET Open ruleset every day, it's syntax tested with Suricata's test mode and loaded with a live rule reload, so there will never be any inspection that doesn't get done. In case of failure, the last ruleset is still in effect. Custom rules are stored in a separate file in version control, and are never overwritten by changes to ET rules. All numeric thresholds (rule thresholds, flow timeouts $T_a$ and $T_i$, $\tau$, $\theta$ values, $\Theta$, block durations) are read from one configuration file with documented defaults.

\subsection{Model Packaging and Versioning}\label{sec:6.6.2}
\label{sec:modelpackaging}
\noindent Each model package contains the model file, the list of features ordered by version of the extractor, the class list and the training date and metrics. The ML scorer rejects any package, whose feature list is incompatible with the running extractor, at load time. XGBoost models are stored in their native JSON format, not as Python pickles, as loading a pickle can run arbitrary code. scikit-learn models are stored in joblib files, and only loaded from the registry directory which is writable only by the deployment user. The last package is preserved for rollback in case of a bad model.

\subsection{Engineering Trade-offs}\label{sec:6.6.3}
\begin{itemize}
    \item \textbf{Detection speed vs.\ accuracy:} ML verdicts are per flow, not per packet (Section~\ref{sec:mltiming}), sacrificing a short delay for ML-detected attacks and eliminating any additional forward delay.
    \item \textbf{False positives vs.\ missed attacks:} the calibration percentile $p$ and the block thresholds are the explicit controls. Defaults prefer fewer false positives as the loss of trust on a home network is fast.
    \item \textbf{Availability vs.\ security:} selected at deployment time (failure mode), default is fail-open for homes.
\end{itemize}

\subsection{Coding Guidelines and Conventions}\label{sec:6.6.4}
\noindent Python code adheres to PEP\~8, uses type hints and runs through a linter and type-checker as part of the continuous integration. Each service is a separate package with one exposed entry point. All event bus messages are versioned JSON with a schema. This allows producers and consumers to be upgraded separately. All logging is structured JSON with timestamp, component name and identifier for either a flow or host. This enables events to be followed through services.

\subsection{Testing Plan}\label{sec:6.6.6}
\begin{enumerate}
    \item \textbf{Unit tests} for each algorithm: flow assembly on crafted PCAPs, JA3 computation against published reference hashes, threshold calibration, fusion rules and the enforcer's allowlist, rate limit and back-off.
    \item \textbf{Integration tests} that replay labelled PCAPs through the full pipeline on a test host and compare verdicts with labels.
    \item \textbf{Live attack tests} on the isolated lab network, executing each in-scope attack from the attacker machine against our own test devices.
    \item \textbf{Performance tests} for latency, throughput and resource use (Table~\ref{tab:sysperf}).
    \item \textbf{Fault-injection tests:} each service is killed or frozen under load in each failure mode, and recovery time and traffic impact are recorded.
    \item \textbf{Soak test:} the system runs for at least one week on a real home network in alert-only mode to measure false positives before blocking is enabled.
\end{enumerate}

\subsection{Build and Deployment}\label{sec:6.6.8}
\noindent The system is installed on a clean Debian image with one installation script, which installs system packages ( Suricata, hostapd, dnsmasq, ipset, Redis ), creates a Python virtual environment with pinned versions of dependencies, copies the configuration and active model package, and enables the systemd units in dependency order: data plane first, then Suricata, and then the rest. Only one service is upgraded at a time and that one service is restarted. Each service is supervised and the failure mode is enforced at kernel level, so that an upgrade does not leave the network with no behaviour.

\subsection{Maintenance}\label{sec:6.6.9}
\noindent Routine maintenance is automated: daily rule updates, weekly threshold recalibration (see Algorithm~\ref{alg:calibration}), and purging logs and flow-records outside of the retention window. Models are retrained offline when new datasets are available, or the dashboard indicates that the alert rate is increasing that is not explained by calibration, or when new classes of attacks become available. The health history report on the Dashboard indicates to the owner when the system was operating in a degraded or failed condition.

\section{Conclusion}\label{sec:6.7}
\label{sec:ch6conclusion}
\noindent In this chapter we translated the methodology of Chapter~\ref{chap:approach} into a concrete design. The NIDPS is a single Linux host, with five runtime subsystems (data plane, detection, decision and response, management and reporting, and reliability), and an offline training pipeline. The main architectural decisions are that the forwarding path is short, encrypted traffic is analysed only via metadata, that training is done offline and thresholds are be calibrated online, that components are separated with the supervised services communicating with each other via an event bus, and that blocking and failure behaviour is controlled by the kernel. The class diagram establishes a common Detector interface which allows quick addition of new detectors, and restricts the number of firewall changes to only one Enforcer. The policies relating to rule and model management, testing, traceability and deployment complete the design, and link each policy goal with the component responsible for it and the test for it.
